# Personal 资源状态与组件协作

本文记录 Input、Task、Routine、Topic 的目标状态模型与更新方案。Conditions、Task/Routine 状态拆分及相应 API 升版尚未落地；当前实现以各资源 Schema 为准。资源版本规则见 [Resource](plugin/resource.md#api-版本与演进)。

## 对象与写入责任

Input 保存收到的事实，Task 承担有限目标，Routine 承担持续职责，Topic 保存主题及其认识。Route、Chief、Weave 围绕这些对象工作；对象的状态描述业务事实，字段命名不依赖具体 Agent 实现。

Reconciler 接收资源变化，完成确定性处理，并安排优先级、接纳、等待与重试；需要上下文判断时调用 Agent。Agent 通过工具提交判断与动作，资源事务校验范围、身份、版本和执行归属。各组件依赖持久事实协调，事件只用于唤醒。

| 事实 | 写入责任 |
| --- | --- |
| Input 当前 Topic | Route 首次绑定；Chief 在合法树范围内调整 |
| 首次路由回执 | 首次分派时产生，完成后保留 |
| Input 研判 | Reconciler 原子接纳；Chief 提交结论与 Work 交接 |
| Work 对 Input 的办理 | 对应 Work 的 Reconciler 应用请求；Agent 或确定性规则确认结果 |
| Topic 父子关系 | Chief 局部整理；Weave 全局归拢 |
| 对外状态条件 | 每种条件明确一个负责汇总结论的维护者 |

同一字段存在多个合法写入者时，声明允许写入的阶段、范围和版本前提，不能依赖最后写入覆盖。执行结束、研判完成、目标达成和 Output 送达是不同事实。

## Status 的三类内容

| 内容 | 用途 | 示例 |
| --- | --- | --- |
| 具体事实与回执 | 承载当前关系、进展和恢复依据 | Topic 引用、研判结论、Work 办理回执、子主题吸收版本 |
| conditions | 向用户和协作组件提供稳定的状态判断 | 已研判、目标达成、需要用户介入 |
| 调谐进度 | 使 Reconciler 能从持久状态继续 | 已处理版本、重试时间、下次维护时间 |

详细执行轨迹独立保存，status 不无限追加模型调用、工具输出和每次 Reconcile 日志。防止重复办理所需的接纳与完成回执是业务事实，不能降级为可能过期或丢失的诊断事件。

## 可共享片段与对象专属状态

共享小而稳定的片段，由对象按语义组合；不建立包含大量可选字段的通用 BaseStatus。

| 片段 | Input | Task | Routine | Topic |
| --- | --- | --- | --- | --- |
| 当前 Topic 引用 | 是 | 是 | 是 | 否，父子关系使用 parentRef |
| summary / recent | 否，解释保存在研判结果 | 是 | 是 | 是 |
| 原生 Agent 会话引用 | 否，只引用处理执行 | 是 | 是 | 是，root 拥有活跃 Chief |
| 当前 execution | 否，接纳记录关联外部执行 | 是 | 是 | 是 |
| 最近组织调整记录 | 是 | 是 | 是 | 是 |
| Condition 基础结构 | 是 | 是 | 是 | 是 |
| 操作回执基础结构 | 按具体操作使用 | 按具体操作使用 | 按具体操作使用 | 按具体操作使用 |

组织调整记录保存操作者、时间、原因和前后关系；共享记录结构不抹平材料迁移与主题重组的区别。操作回执可共享执行引用、时间和错误结构，各操作的结果及完成条件独立定义。

### Input

保留不可变原文与来源。status.topic 表达唯一当前归属；route 保存首次路由处理；assess 保存唯一研判与接纳；handle 按 Work UID 保存请求和办理回执。修改归属不清空处理历史，不重新执行已完成处理。Input 不拥有独立 Agent，不增加用于持续积累认识的顶层 summary/recent。

### Task 与 Routine

共享当前归属、认识、会话、执行、等待原因、最近报告及恢复核对信息。结果需要注明对应的目标或职责版本，使用 metadata.generation 表达 spec 的修订依据，避免另建含义相同的计数器。

Task 保存当前目标版本的完成结果与依据。Routine 保存触发消费进度、当前或最近一次触发实例的结果，以及下一次计划时间；一次执行成功不表示持续职责完成。

拆开调度、执行和业务结果，不再让同一个枚举同时承担 running、scheduled、done 等不同维度。暂停若表达用户期望，归入 spec；status 表达是否已经落实以及剩余在途执行。外部效果不确定时先核对，不以重试代替恢复判断。

### Topic

共享认识与执行片段，独有子主题认识吸收记录、结构变化处理进度、真实业务活动时间、维护时机与吸收重试信息。已有子主题版本记录继续承载依赖依据；不能仅用 Topic 自己的 generation 判断子树认识是否已更新。

## Conditions 契约

引入 conditions 作为统一状态判断接口，补充具体事实与业务回执。集合按 type 唯一，字段为 type、status（True/False/Unknown）、reason、message、lastTransitionTime；条件依据 spec 时记录 observedGeneration。缺失条件表示尚无判断，不推断为成功。未声明适用的条件不参与通用健康计算。

reason 是稳定的机器分类，message 说明具体问题。lastTransitionTime 仅在条件状态变化时更新，不随每次 Reconcile 刷新。条件类型及含义是 API 契约，不按 Agent 命名，不要求四类对象拥有相同条件，也不把所有条件取 AND 作为通用 Ready。

以下候选在落地时按实际查询、展示与协作需求选择，并确定唯一维护者：

| 对象 | 候选条件 | 语义 |
| --- | --- | --- |
| Input | Assessed | 已产生持久化研判结论，不代表所有办理已完成 |
| Input | HandlingComplete | 已建立的办理义务全部结束，成功与否读取各回执；研判尚未完成时不能宣布完成，研判完成且无需办理时成立 |
| Task | Succeeded | 当前目标版本已达成，旧版本成功不能确认新目标 |
| Routine | Operational | 持续职责具备按约定接收和处理触发的能力；等待下一轮是正常状态，暂停或阻塞原因需明确 |
| Topic | SummaryCurrent | 当前需要吸收的子主题认识版本已处理，不代表模型判断必然正确 |
| 按需适用 | NeedsAttention | 存在必须由用户介入的问题，明确解除条件 |

能在同一事务计算的条件与事实一起写入。跨资源的异步判断保存依赖版本，由 Watch 与 Reconcile 重算；自身 observedGeneration 无法代表外部依赖的新旧。消费者根据条件契约识别过期结论，不能将旧 True 当作对新状态的保证。

Conditions 提供稳定消费接口，不自动提供数据兼容，也不代替并发控制、幂等与安全交接。

## 更新顺序与验证

1. 定义 Condition 基础结构、更新规则与各条件维护者，选定真实消费者。
2. 按对象拆分 Schema：Input 保留处理回执；Task/Routine 分离目标完成与触发进度；Topic 保留子树版本依据。共享片段不改变对象的业务责任。
3. 对发生不兼容结构或语义变化的 Kind 升级 apiVersion（当前 v1alpha1 的下一版为 v1alpha2）。同步定义、创建入口、引用、索引、工具与测试。兼容性新增不强制升版。
4. 将条件计算接入所属 Reconciler 和业务提交事务，UI 与跨组件判断按稳定条件读取，详细诊断仍展开具体事实。
5. 验证多组件更新不会覆盖彼此事实；条件与回执一致；重启不重复执行；spec 或依赖版本变化后不会误用旧结论；Task 完成和 Routine 单次完成具有不同生命周期。

当前开发阶段只实现新版本契约，不实现旧版本读取、转换、迁移或兼容回退；也不自动删除旧记录。升版用于明确边界，不宣称旧数据已转换或可继续使用。历史数据治理作为未来独立需求处理。
