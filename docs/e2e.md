# 真实 Channel 验证

`npm run check` 使用真实 Plugin Worker 和模拟 Harness Adapter。以下验收通过已部署服务、[Web / Feishu Channel](channel/README.md)、真实 Chief 与 Pi Harness 执行，不计入该自动测试结果。测试限定在独立开发实例和测试工作目录；记录 `/health` 的 revision、测试会话名、时间、Work id、状态与回复，证据放在工作区测试产物目录中，不提交登录态或完整私人会话。

前提：服务正常运行，Pi / Chief 模型与认证已配置，网页能够连接。Hooks 信任与工具权限按网页显示的具体请求由用户决定；请求超时算阻塞或失败，不算通过。相同消息编号只做传输去重；Chief 失败后需核对状态，再用新消息交办。运行前在服务的工作目录中准备只含测试数据的文件，验收完成后暂停测试安排。

## 普通问答

在测试文件中写入一个随机标记，不把标记放入提示词。通过网页交办“读取这个文件并告诉我验证标记，不修改文件”。

验收：Chief 直接回答，回复含文件中的准确标记；Pi 执行记录包含实际读取文件；没有创建 Work。刷新网页后仍能看到同一回复。HTTP 接收成功不足以判定通过。

## 进度说明与最终结果

明确要求创建一个只读文件检查 Task，要求执行时先简短说明准备做什么，再调用工具读取文件，最后给出结构化结果。记录原生 Harness 中分别标记为 `commentary` 和 `final_answer` 的消息。

验收：查询命令成功，最终 JSON 独立进入 Turn 的 `finalText`，进度文字仍保留在 `agentText`；事项为 done，回复包含真实读取结果。不能仅用“不输出进度说明”的请求绕开此场景。

## 追问与恢复

交办“创建一次性事项：替我写一段欢迎语，先问我希望使用的称呼，收到回答后再完成，不调用外部系统”。

验收：产生 Task，执行后为 waiting，问题可见；在 waiting 状态重启开发服务并刷新网页，问题仍在。回答一个唯一称呼，确认沿用同一个 Work id，最终为 done，欢迎语使用这个称呼。核对没有新建重复事项。

## 定期处理

交办“每分钟检查指定测试文件。首次只记录基线，有变化时告诉我变化后的标记，没变化时不要通知，不修改文件”。

验收：产生 Routine 并有 nextAt；首次执行后仍为 scheduled。关闭页面，在测试目录修改标记，等待下个触发后重新打开页面，确认收到正确变化通知。同一内容再触发一轮不重复通知。发送暂停请求，确认为 paused 且 nextAt 为空；越过下个周期后执行次数不增加。恢复后仍使用原 Work id；验证完成后再次暂停。

将每一项记为通过、失败或阻塞，并注明实际覆盖的步骤。缺失权限决定、模型连接失败、页面未执行或未等待周期，都不能用模拟测试结果替代。

## 持续委托与主动沟通

通过一个跨时间的有限目标检验委托连续性：在测试目录准备标记为 pending 的状态文件，交办“创建事项，跟进这个测试交付直到状态变为 ready；等待期间每分钟检查，ready 后读取结果并先问我交付名称，收到回答后写入独立结果文件，再告诉我文件位置与验证结果”。

记录 Task id 与执行次数。在工作等待外部变化时关闭页面、重启开发服务，将状态文件改为 ready；重新打开页面确认同一工作继续推进并提出问题。等待用户回答期间再次重启，回复一个唯一交付名称，检查实际文件内容与完成依据。Task 达到目标后结束，不因曾经周期检查而变成 Routine。

另在独立测试会话开启 Heartbeat，使用短间隔观察多个周期。没有新情况时不发送例行消息；出现与已有委托相关的变化时检查 Chief 是否先查询、关联原工作，再推进、告知或提出必要问题。收到普通进展通知后没有新的用户输入或外部变化，下一周期不重复发送同一通知。遇到需要用户决定的事项，检查问题是否包含已查明事实与清晰选择，且没有先执行待确认动作。使用者接收 say 后不必回答，ask / confirm 的答案则用于继续处理对应问题。

验收同时记录以下结果：

- 委托是否保持同一身份，重启与等待后是否需要用户重新描述目标。
- 已生效的动作是否重复，消息是否漏发或重复；记录结果文件写入轨迹，而非仅检查最终内容。
- 完成状态是否有对应的外部证据，最终通知是否与证据一致。
- 用户为催进度、补充已经提供的信息或纠正操作而额外介入的次数；必要的业务决策单独记录。
- 没有变化时的打扰次数，以及从有效变化到推进或通知的时间。

逐阶段保存证据并标注通过、失败或阻塞；测试脚本中的预定输入不算额外介入。验收结束后关闭 Heartbeat、暂停未完成测试工作。这些观察用来判断持续跟进是否减少用户负担，不能用运行时长或消息数量替代。

## 会话切换与进展

在两个独立会话中分别发送不同的验证标记。从 Web 左栏切换会话，检查消息、已保存的思考与工具过程、Task / Routine 均属于所选会话。刷新和浏览器返回后，所选会话由 URL 恢复；发送消息仍进入该会话。

在 Chief 执行期间观察真实流式状态，确认过程与回答位于同一个回复块，外层能整体折叠，内部两块能分别展开、收起。手动改变折叠状态后继续接收增量与后续消息，确认选择保留。完成后外层默认展开，内部过程与回答显示缩略预览，分别展开能看见完整记录与 Markdown；提问与中断提示默认可见。刷新页面，确认同轮过程与最终答案仍在同一回复块，且没有重复答案。Core Interaction 是 Session 级收件区，不能将它跨会话可见误记为消息隔离失败。Feishu 验证另按 [接入文档](channel/feishu.md) 执行，并记录真实投递证据。


## 飞书流式卡片

按 [Feishu](channel/feishu.md) 配置 CardKit 权限后，在机器人单聊发起需要读文件和多次查询的问题。确认先出现处理状态，再看到真实思考或工具进展和文字更新；卡片正文可以整体折叠，内部过程与回答能独立折叠，结束后外层默认展开，内部过程与回答显示缩略预览，分别展开保留完整记录与正文，没有重复文本。

再要求 Chief 先提问后继续，确认等待时关闭流式、回答后恢复同一卡片。检查超长答案的完整分段文本与卡片失败时的最终消息回退。记录机器人版本、会话、消息与卡片投递证据，模拟请求不算真实飞书客户端验收。

## 飞书群内 @机器人

按 Feishu 文档开通群内 @接收权限并将机器人加入测试群。@Aide 交办只读测试文件核验，确认日志的 chatType=group、模型输入没有 @占位符，结果和流式卡片回到该群。在另一个群与单聊分别发送不同标记，确认消息和工作按 chat_id 隔离。同一群内用户共用会话。

在原群发送不 @、只 @其他机器人、只 @所有人的消息，核对没有新建 Chief 输入；群内追问须再次 @Aide。记录实际群事件和出站结果，不通过本地合成事件宣称平台权限已验证。
